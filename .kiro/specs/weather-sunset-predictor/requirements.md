# 需求文档

## 简介

天气晚霞预测器是一个Web应用程序，允许用户查询天气信息并预测火烧云（晚霞）出现的可能性和质量。系统通过Windy API获取气象数据，分析多个气象参数（云层、湿度、能见度等），为用户提供晚霞观赏的最佳时机建议。

## 术语表

- **系统（System）**: 天气晚霞预测器Web应用程序
- **Windy_API**: Windy提供的Point Forecast API服务
- **火烧云（Sunset_Glow）**: 日落时分天空中出现的红色或橙色云彩现象
- **预测质量（Prediction_Quality）**: 火烧云出现可能性的评分，范围0-100
- **气象参数（Weather_Parameters）**: 包括温度、湿度、云层、风速、气压等数据
- **API_Key**: 用户的Windy API访问密钥

## 需求

### 需求 1：API密钥管理

**用户故事：** 作为用户，我想要安全地配置我的Windy API密钥，以便系统能够获取天气数据。

#### 验收标准

1. 当用户首次访问应用时，系统应显示API密钥配置界面
2. 当用户输入API密钥时，系统应将其存储在浏览器本地存储中
3. 当用户提交API密钥后，系统应验证密钥的有效性
4. 如果API密钥无效，则系统应显示错误消息并允许重新输入
5. 当API密钥已配置时，系统应允许用户查看和修改密钥

### 需求 2：位置选择

**用户故事：** 作为用户，我想要选择查询位置，以便获取特定地点的天气和晚霞预测。

#### 验收标准

1. 当用户访问主界面时，系统应提供位置输入功能
2. 当用户输入位置名称时，系统应将其转换为经纬度坐标
3. 当用户点击"使用当前位置"按钮时，系统应请求浏览器地理位置权限
4. 如果用户授予位置权限，则系统应获取当前GPS坐标
5. 当位置无法解析时，系统应显示友好的错误提示

### 需求 3：天气数据获取

**用户故事：** 作为用户，我想要查看当前和未来的天气信息，以便了解基本气象条件。

#### 验收标准

1. 当用户选择位置后，系统应调用Windy API获取天气数据
2. 当API请求发送时，系统应使用POST方法访问 https://api.windy.com/api/point-forecast/v2
3. 系统应请求以下气象参数：temp、rh、clouds、wind、pressure、visibility
4. 当API返回数据时，系统应解析并存储未来48小时的预测数据
5. 如果API请求失败，则系统应显示错误信息并允许重试

### 需求 4：基本天气显示

**用户故事：** 作为用户，我想要看到清晰的天气信息展示，以便快速了解当前气象状况。

#### 验收标准

1. 当天气数据加载完成时，系统应显示当前温度、湿度、风速和云量
2. 系统应以摄氏度显示温度值
3. 系统应以百分比显示湿度和云量
4. 系统应以公里/小时显示风速
5. 当显示天气信息时，系统应包含适当的图标和视觉元素

### 需求 5：火烧云预测算法

**用户故事：** 作为用户，我想要获得准确的火烧云预测，以便决定是否外出观赏朝霞和晚霞。

#### 验收标准

1. 当系统计算火烧云质量时，系统应分析中高层云量（30-70%为最佳）
2. 当系统计算火烧云质量时，系统应评估相对湿度（30-70%为最佳范围）
3. 当系统计算火烧云质量时，系统应考虑能见度因素（高能见度加分）
4. 当系统计算火烧云质量时，系统应检查低层云量（低层云少为佳）
5. 系统应输出0-100的预测质量评分
6. 当评分高于70时，系统应标记为"优秀"观赏条件
7. 当评分在40-70之间时，系统应标记为"良好"观赏条件
8. 当评分低于40时，系统应标记为"一般"观赏条件

### 需求 6：预测结果展示

**用户故事：** 作为用户，我想要看到直观的预测结果，以便快速理解朝霞和晚霞出现的可能性。

#### 验收标准

1. 当预测计算完成时，系统应显示预测质量评分
2. 系统应使用颜色编码表示预测质量（绿色=优秀，黄色=良好，灰色=一般）
3. 系统应显示影响预测的关键气象因素
4. 系统应显示最佳观赏时间（日落前后30分钟）
5. 当显示预测结果时，系统应提供详细的气象条件说明

### 需求 7：未来预测时间线

**用户故事：** 作为用户，我想要查看未来几天的晚霞预测，以便提前计划观赏活动。

#### 验收标准

1. 当天气数据可用时，系统应计算未来3天的晚霞预测
2. 系统应为每天的日落时间生成独立的预测评分
3. 系统应以时间线或列表形式展示多日预测
4. 当用户点击某一天的预测时，系统应显示该天的详细气象数据
5. 系统应高亮显示预测质量最高的日期

### 需求 8：响应式设计

**用户故事：** 作为用户，我想要在不同设备上使用应用，以便随时随地查询晚霞预测。

#### 验收标准

1. 当用户在移动设备上访问时，系统应调整布局以适应小屏幕
2. 当用户在桌面设备上访问时，系统应充分利用大屏幕空间
3. 系统应在所有主流浏览器（Chrome、Firefox、Safari、Edge）上正常工作
4. 当屏幕方向改变时，系统应自动调整布局
5. 系统应确保所有交互元素在触摸屏上易于操作

### 需求 9：数据刷新

**用户故事：** 作为用户，我想要刷新天气数据，以便获取最新的预测信息。

#### 验收标准

1. 系统应提供手动刷新按钮
2. 当用户点击刷新按钮时，系统应重新请求Windy API数据
3. 当数据刷新时，系统应显示加载指示器
4. 系统应缓存数据30分钟以减少API调用
5. 如果缓存数据未过期，则系统应优先使用缓存数据

### 需求 10：错误处理

**用户故事：** 作为用户，我想要在出现问题时看到清晰的错误信息，以便知道如何解决问题。

#### 验收标准

1. 如果网络连接失败，则系统应显示"网络连接错误"消息
2. 如果API密钥无效，则系统应提示用户检查密钥配置
3. 如果API请求超时，则系统应显示超时错误并提供重试选项
4. 如果位置解析失败，则系统应建议用户尝试不同的位置名称
5. 当发生错误时，系统应保持应用的稳定性，不应崩溃

### 需求 11：天气界面优化

**用户故事：** 作为用户，我想要看到更全面的天气信息和直观的数据可视化，以便更好地了解天气变化趋势和做出决策。

#### 验收标准

1. 当用户查看天气面板时，系统应显示未来7天的每日天气概览
2. 当用户查看每日概览时，系统应显示日期、最高/最低温度、天气图标和降水概率
3. 当用户选择查看今天或明天的详细数据时，系统应显示24小时的小时级预报
4. 当显示小时级温度数据时，系统应使用折线图展示温度变化趋势
5. 当显示小时级降水数据时，系统应使用柱状图展示降水量或降水概率
6. 当显示小时级湿度数据时，系统应使用折线图或面积图展示湿度百分比变化
7. 当显示小时级风速数据时，系统应使用折线图展示风速变化，并用箭头图标显示风向
8. 当显示小时级气压数据时，系统应使用折线图展示气压变化趋势
9. 当显示小时级云量数据时，系统应使用面积图或柱状图展示云层覆盖百分比
10. 系统应支持用户在不同气象参数之间切换查看（温度、降水、湿度、风速、气压、云量）
11. 当显示图表时，系统应使用适当的颜色编码（如温度用蓝→橙→红渐变，降水用蓝色系）
12. 系统应在图表上标注关键数值点，便于用户快速读取数据
13. 当用户在移动设备上查看时，图表应支持横向滚动以显示完整的24小时数据


### 需求 12：朝霞晚霞预测增强功能

**用户故事：** 作为摄影爱好者或观赏者，我想要获得更专业的朝霞和晚霞预测信息，以便更好地规划拍摄或观赏活动。

#### 验收标准

1. 当系统显示预测时，系统应同时显示日出和日落的精确时间
2. 当系统显示预测时，系统应标注"黄金时段"（Golden Hour）的时间范围（日出后/日落前30-60分钟）
3. 当系统显示预测时，系统应标注"蓝调时段"（Blue Hour）的时间范围（日出前/日落后20-30分钟）
4. 当系统显示预测时，系统应分别计算和显示朝霞（日出）和晚霞（日落）的独立评分
5. 当预测质量较高时（评分>70），系统应显示太阳方位角信息，帮助用户确定最佳拍摄/观赏方向
6. 系统应提供预测提醒功能，允许用户设置在高质量预测时接收浏览器通知
7. 当用户启用提醒时，系统应允许用户自定义提醒阈值（如评分>70时提醒）
8. 当用户启用提醒时，系统应在符合条件时发送浏览器通知，包含日期、时间和评分信息
9. 系统应支持用户收藏多个位置，并在位置列表中快速切换
10. 当用户收藏位置时，系统应保存位置名称和坐标到本地存储
11. 当用户查看预测时，系统应显示云层分层信息，包括高云（>6km）、中云（2-6km）、低云（<2km）的覆盖百分比
12. 当显示云层信息时，系统应用不同颜色或图标区分不同高度的云层
13. 当显示预测详情时，系统应说明各层云对朝霞/晚霞效果的影响（如"中高云适中，有利于火烧云形成"）


### 需求 13：最近搜索历史

**用户故事：** 作为用户，我想要快速访问最近搜索过的城市，以便无需重复输入常用位置。

#### 验收标准

1. 当用户成功查询某个位置的天气后，系统应将该位置保存到搜索历史中
2. 系统应在本地存储中保存最近搜索的5个城市（包括城市名称和坐标）
3. 当搜索历史超过5个时，系统应自动删除最早的记录，保持最多5个
4. 当用户点击位置输入框时，系统应显示最近搜索历史的下拉列表
5. 当用户点击历史记录中的某个城市时，系统应自动填充该城市并加载天气数据
6. 当显示搜索历史时，系统应按时间倒序排列（最新的在最上面）
7. 系统应提供清除单个历史记录的功能（如每个记录旁边的删除按钮）
8. 系统应提供清除全部历史记录的功能
9. 当用户搜索已存在于历史中的城市时，系统应将该城市移到历史列表的最前面，而不是创建重复记录
10. 当历史记录为空时，系统应显示提示信息（如"暂无搜索历史"）


### 需求 14：多语言支持

**用户故事：** 作为用户，我想要使用母语或其他熟悉语言来浏览应用，以便更好地理解和使用应用功能。

#### 验收标准

1. 当用户访问应用时，系统应自动检测浏览器的语言设置
2. 当检测到的语言在支持列表中时，系统应自动切换到该语言
3. 当检测到的语言不在支持列表中时，系统应使用默认语言（简体中文）
4. 系统应提供语言切换功能，允许用户手动选择界面语言
5. 系统应在设置或导航栏中提供语言选择器（下拉菜单或按钮）
6. 当用户切换语言时，系统应保存语言偏好到本地存储
7. 当用户切换语言后，系统应刷新界面并应用新语言
8. 系统应支持至少10种语言：简体中文（zh-CN）、繁体中文（zh-TW）、英语（en-US）、日语（ja-JP）、韩语（ko-KR）、越南语（vi-VN）、法语（fr-FR）、西班牙语（es-ES）、意大利语（it-IT）、阿拉伯语（ar-SA）
9. 当用户使用阿拉伯语时，系统应正确处理RTL（Right-to-Left）布局
10. 系统应为RTL语言镜像必要的UI元素（如图标、边距、对齐方式）
11. 当显示日期时，系统应根据语言自动格式化（如"2026年1月25日" vs "January 25, 2026"）
12. 当显示数字时，系统应根据语言自动格式化千分位和小数点（如"1,234.56" vs "1.234,56"）
13. 当显示时间时，系统应根据语言使用12小时制或24小时制（英语国家倾向12小时制）
14. 当显示百分比时，系统应根据语言格式化（如"85%"在不同语言中格式一致）
15. 系统应提供语言切换确认机制，防止用户误操作切换语言
16. 当切换语言时，系统应保留当前的用户数据（如位置、API密钥、收藏列表）
17. 系统应在所有界面文本中支持翻译（包括标题、按钮、提示信息、错误消息）
18. 当翻译文本缺失时，系统应回退到默认语言的对应文本


### 需求 15：后端代理 Windy API 与密钥保护

**用户故事：**  
作为系统所有者，我希望 Windy API 密钥只保存在后端，由后端统一代理调用 Windy API，这样可以避免在前端代码或网络请求中暴露密钥，降低被滥用和泄露的风险。

#### 验收标准

1. 系统应提供一个后端天气数据接口（例如 `/api/weather/forecast`），用于替代前端直接访问 `https://api.windy.com/api/point-forecast/v2`。  
2. 后端应从环境变量或安全配置文件中读取 Windy API 密钥（如 `WINDY_API_KEY`），前端和代码仓库中不得出现真实密钥。  
3. 当前端请求后端天气接口时，后端应使用配置中的密钥向 Windy API 发起请求，并将 Windy 返回的数据解析为系统所需格式再返回给前端。  
4. 浏览器开发者工具中（包括页面源代码和 Network 请求信息），不应出现 Windy API 密钥或可推断出该密钥的敏感字段。  
5. 当后端调用 Windy API 失败（如网络错误、超时、配额限制、无效坐标等）时，后端应返回明确的错误状态和人类可读的错误信息，前端应展示友好的错误提示并允许重试。  
6. 后端接口应支持基础的访问日志记录，以便后续排查问题和监控调用情况（例如记录请求时间、坐标参数、Windy 响应状态等，不记录敏感密钥本身）。


### 需求 16：统一设置面板

**用户故事：**  
作为用户，我希望有一个统一的设置面板，可以在一个地方集中管理与应用相关的配置（如 API 使用方式、通知、语言等），以便更方便地自定义应用行为，而不需要在多个位置查找和修改设置。

#### 验收标准

1. 系统应在主界面提供明显可见的「设置」入口（例如右上角齿轮按钮），点击后打开设置面板或模态框。  
2. 设置面板至少应包含以下分组区域：  
   - 「数据源与网络」：展示当前使用的 API 模式（真实 Windy 后端代理 / 模拟数据），并提供只读说明文案（不在前端填写密钥）。  
   - 「通知与提醒」：集中管理晚霞预测通知的开关、评分阈值等（可复用现有通知设置功能的 UI/逻辑）。  
   - 「语言与显示」：展示当前语言选择入口（可复用现有语言选择器），并提供与界面相关的基础说明。  
3. 当用户在设置面板中修改通知开关或阈值时，系统应立即保存并生效，且与现有通知功能使用相同的数据存储逻辑（如 `StorageService` 中的通知设置）。  
4. 当用户在设置面板中切换语言时，系统应立即更新界面文案，与现有多语言机制保持一致（包括标题、按钮、提示信息等）。  
5. 设置面板在桌面端和移动端都应具备良好的可用性：  
   - 在小屏幕上应自适应布局，无内容被裁剪或难以点击的情况；  
   - 关闭按钮或返回操作明显可见，可通过点击遮罩或显式按钮关闭。  
6. 设置面板的所有文案应接入多语言系统，至少覆盖当前支持的语言（如 zh-CN、en-US 等），避免出现硬编码的单一语言文本。  
7. 若后续引入更多可配置项（例如主题、单位制等），应能够在不破坏现有交互的前提下扩展到设置面板中。


### 需求 17：个性化设置（单位、主题、默认位置）

**用户故事：**  
作为经常使用本应用的用户，我希望能够自定义温度/风速等显示单位、界面主题（暗色/自适应）以及默认位置，这样每次打开应用时都能看到符合自己习惯的界面和数据。

#### 验收标准

1. 系统应允许用户在设置面板中选择 **温度单位**（至少支持 ℃ / ℉），并在所有相关界面中按所选单位显示温度值（包括当前天气、未来预报、图表等）。  
2. 系统应允许用户在设置面板中选择 **风速单位**（如 m/s、km/h，若已有单位规范可按现有约定扩展），并在所有显示风速的地方统一采用用户选择的单位。  
3. 当用户修改单位设置后，界面上已有的数据展示应在不刷新页面的前提下更新为新单位，避免需手动重新搜索。  
4. 系统应提供 **主题设置** 选项，至少包括：  
   - 明亮模式（Light）  
   - 暗色模式（Dark）  
   - 自适应系统（Follow System，优先跟随操作系统 / 浏览器的深浅色偏好）  
5. 当用户切换主题时，界面应立即应用新主题（包括背景、文字、卡片、图表配色等），并在后续访问时保持用户上次选择的主题。

### 需求 20：火烧云地图覆盖层

**用户故事：** 作为用户，我想要在地图上直接看到火烧云预测的地理分布热力图，以便直观了解区域内的火烧云观赏潜力分布。

#### 参考文档

- NOAA GFS 数据: https://www.ncei.noaa.gov/products/weather-climate-models/global-forecast-system
- GRIB2 数据格式: https://www.nco.ncep.noaa.gov/pmb/docs/grib2/grib2_doc/

#### 验收标准

1. 当用户查看地图预测时，系统应提供"火烧云覆盖层"选项
2. 当用户启用火烧云覆盖层时，系统应获取周边区域（约200-300公里范围）的GFS气象数据
3. 当系统获取GFS数据时，系统应下载以下变量：
   - TCDC (Total Cloud Cover) - 总云量
   - LCDC (Low Cloud Cover) - 低层云量（<2km）
   - MCDC (Middle Cloud Cover) - 中层云量（2-6km）
   - HCDC (High Cloud Cover) - 高层云量（>6km）
4. 当系统处理GFS数据时，系统应对每个像素点应用"光路追踪+云量评分"算法：
   - 向西（日落方向）检查邻近像素的LCDC值以评估光路阻隔
   - 结合本地的MCDC/HCDC计算火烧云概率值（0.0-1.0）
5. 当系统生成覆盖层图像时，系统应创建带透明通道的PNG图片：
   - 概率0 = 完全透明
   - 概率100 = 红色/橙色渐变，不透明度60%
   - 图像分辨率适配地图缩放级别（建议512x512或1024x1024）
6. 当覆盖层生成完成后，系统应记录图像的四个角坐标（Bounds）以便准确贴图
7. 当系统显示覆盖层时，系统应在Windy地图上叠加PNG图像作为自定义图层
8. 当覆盖层显示时，系统应提供图例说明（颜色含义：红橙色=高概率，黄色=中等概率，灰色=低概率）
9. 当用户调整地图位置或缩放时，系统应重新获取对应区域的GFS数据并更新覆盖层
10. 当GFS数据获取失败时，系统应显示错误提示并回退到雷达图模式
11. 系统应缓存生成的覆盖层图像（有效期30分钟）以减少重复计算
12. 当用户在移动设备上查看时，覆盖层应支持触摸缩放和平移
13. 系统应提供覆盖层刷新按钮，允许用户手动更新数据
14. 当覆盖层加载时，系统应显示加载动画或进度指示器
15. 系统应支持切换朝霞和晚霞的覆盖层显示

### 需求 22：前后端分离架构重构

**用户故事：** 作为开发者/系统维护者，我希望将核心预测算法和业务逻辑迁移到后端，实现真正的前后端分离架构，以便：
- 支持多平台客户端（Web、iOS、Android、小程序）复用同一套后端 API
- 减少前端代码体积和浏览器 CPU 占用
- 支持后端缓存和算法 A/B 测试
- 提高系统可维护性和可扩展性

#### 验收标准

**Phase 1：核心预测算法后端化**

1. 后端应提供预测计算 API `POST /api/prediction/calculate`，接收天气数据、日期、坐标、预测类型，返回预测结果 JSON
2. 预测结果应包含：评分（score）、质量等级（quality）、各因素得分（factors）、日出/日落时间、黄金时段、蓝调时段
3. 后端预测算法应与当前前端算法（`SunsetPredictionService`）计算结果保持一致
4. 前端应改为调用后端 API 获取预测结果，不再在浏览器端执行预测算法
5. 系统应提供算法版本标识，支持未来算法迭代和 A/B 测试

**Phase 2：周边采样聚合**

6. 后端应提供周边预测聚合 API `POST /api/prediction/surrounding`，一次请求返回 8 个方向的预测结果
7. 后端应在服务端并行获取 8 个方向点的天气数据，减少网络往返次数（从 8×RTT 降至 1×RTT）
8. 前端周边火烧云功能应改为调用聚合 API，不再发起多个并行请求
9. 后端应支持周边数据缓存，相同位置/半径/时间的请求可复用缓存

**Phase 3：增强预测模型后端化**

10. 后端应提供增强预测 API `POST /api/prediction/enhanced`，包含画布评分、光路通透评分等高级功能
11. 后端应支持预测模型选择参数，允许客户端指定使用基础或增强模型
12. 增强预测 API 应保持与当前前端 `EnhancedSunsetPredictionService` 计算结果一致

**API 设计规范**

13. 所有预测 API 应返回统一的响应格式：`{ success: boolean, data: object, error?: { code, message } }`
14. API 应支持请求参数验证，对无效参数返回 400 错误码和描述性错误信息
15. API 应记录请求日志，包含请求参数、响应时间、错误信息（如有）

**性能要求**

16. 单点预测 API 响应时间应 < 500ms（不含天气数据获取时间）
17. 周边聚合 API 响应时间应 < 2000ms（包含 8 个点的天气数据获取）
18. 后端预测计算应比前端快（得益于 Node.js 优化）

**兼容性**

19. 前端应保留对旧 API 的兼容，支持渐进式迁移
20. 系统应提供 API 版本管理机制，便于未来 API 升级
